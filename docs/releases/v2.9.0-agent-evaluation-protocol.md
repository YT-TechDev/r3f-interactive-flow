## Two-phase structure

- **Phase A** (this document): a deterministic harness — immutable task
  contracts, reference fixtures, negative fixtures, and a repository command
  that never contacts an AI service. Phase A alone makes no claim about any
  agent's actual output.
- **Phase B**: exactly one explicitly approved controlled external-agent
  evaluation run per task, using the harness built in Phase A. Phase B
  requires explicit owner approval of a specific run record (service, model,
  run count, task IDs, data boundary, spend boundary) before it starts.

## What the harness evaluates

Five fixed task IDs, each a small, isolated Vite + React + React Three Fiber
consumer built from the exact packed local tarball and the exact pinned
consumer tuple already established by #403/#405:

1. `AGENT-FOUNDATION` — a typed phase tuple, `FlowProvider`, DOM `next`/`prev`/
   `goTo` controls via `useFlow`, and a DOM progress indicator via
   `useFlowProgress`. No Canvas required.
2. `AGENT-CANVAS` — starting from a valid DOM flow with an existing `<Canvas>`
   and an inert scene object, add `useFlowFrame` inside a Canvas-rendered
   component and mutate a ref/Three.js object per frame.
3. `AGENT-INPUT-AND-MOTION` — starting from a valid provider + DOM controls +
   Canvas-bound scene, add `useWheelInput`, `useTouchInput`, and
   `useKeyboardInput` from a DOM/input-layer component, plus an
   application-owned reduced-motion path (no invented package API).
4. `AGENT-REPAIR-IMPORT` — fix one seeded defect: an import from
   `r3f-interactive-flow/react` instead of the package root.
5. `AGENT-REPAIR-CANVAS-BOUNDARY` — fix one seeded defect: `useFlowFrame`
   called from a DOM component outside `<Canvas>`.

Each task's full contract (starting point, required behavior, positive/
negative assertions, allowed/forbidden files, scoring-criteria applicability,
and hard gates) is recorded in
[`validation/agent-public-docs/contracts/agent-public-docs-v1.json`](../../validation/agent-public-docs/contracts/agent-public-docs-v1.json).

## Public documentation input set

The evaluated agent may receive only:

- `README.md`
- `packages/r3f-interactive-flow/README.md`
- `docs/guides/README.md`
- `docs/guides/getting-started.md`
- `docs/guides/core-concepts.md`
- `docs/guides/r3f-usage.md`
- `docs/guides/input-handling.md`
- `docs/guides/accessibility-and-reduced-motion.md`
- `docs/guides/nextjs-usage.md`
- `docs/guides/common-mistakes.md`

A deterministic manifest of these files (relative path, UTF-8 byte length,
SHA-256, baseline commit) lives at
[`validation/agent-public-docs/public-docs-manifest.json`](../../validation/agent-public-docs/public-docs-manifest.json)
and is verified on every `pnpm consumer:agent:verify` run. The evaluated agent
never receives package source, package tests, maintainer docs, `AGENTS.md`,
validation scripts, prior candidate outputs, reference solutions, negative
harness fixtures, private prompts, conversation history, repository Git
history, or environment secrets. Public documentation is never modified by
this Issue; reproduced documentation gaps are handed to #407.

## Deterministic verifier stages

`scripts/verify-agent-public-docs.mjs` (via `pnpm consumer:agent:verify`)
runs, in order:

1. Verify the package build output exists.
2. Verify the public-doc manifest (paths, byte lengths, SHA-256, baseline
   commit).
3. Verify the contract version and the exact five task IDs.
4. Verify every task input fixture is immutable relative to its recorded
   hash.
5. Verify allowed output-file sets and forbidden changes for every fixture.
6. Pack the real local package tarball once.
7. Create one isolated temp consumer and install the exact pinned dependency
   tuple with `npm install --no-audit --no-fund --ignore-scripts`.
8. Require that install to succeed with no fallback.
9. Assert the package and its direct dependencies are real installed copies,
   not repository/workspace resolution.
10. Validate `npm ls --json --all` reports an empty `problems` list and exits
    zero.
11. Validate all five known-good `REFERENCE` outputs: strict TypeScript
    typecheck, a production Vite build, task-specific static assertions, and
    a full score/hard-gate pass.
12. Validate six deliberately broken `HARNESS_NEGATIVE` fixtures (internal
    subpath, `useFlowFrame` outside Canvas, an invented reduced-motion API,
    per-frame React state, a forbidden dependency/file change, and a nested
    unexpected output file).
13. Require each negative fixture to fail for its exact intended reason.
14. For every committed, owner-approved run under
    `validation/agent-public-docs/runs/`, replay the raw candidate output
    deterministically and compare the observed result against the committed
    evidence record.
15. Print a concise evidence summary.
16. Remove the isolated temp consumer.

The command never contacts an AI service and requires no secret. A raw
evaluated-agent task result is allowed to fail; that raw failure does not
make the repository command fail as long as it is accurately recorded and
classified in a committed evidence record (stage 14). The command does fail
when a committed evidence claim does not match deterministic observation, or
when any reference/negative fixture does not behave as the harness itself
declares it should.

## Scoring and hard gates

Eight binary criteria are evaluated per task, each explicitly marked
applicable or not-applicable (with a reason) in the task contract:

1. build/typecheck succeeds
2. required public behavior is implemented
3. package-root imports only
4. React Client Component boundary is correct where applicable
5. Canvas boundary is correct where applicable
6. no invented API or package export
7. no unnecessary runtime dependency or framework coupling
8. change remains inside the fixed task scope

None of the five tasks in this harness involve a Server/Client Component
split (they are plain Vite consumers), so criterion 4 is marked
not-applicable for all five tasks with that stated reason. Hard gates (build/
typecheck success, package-root imports, no invented API, correct required
Canvas boundary, no secret/private-repository exposure) must all pass for a
raw task result to pass; failing any applicable hard gate fails that task
regardless of the numeric score. Scores are never aggregated into a universal
model score, vendor leaderboard, or marketing claim — only task-level
evidence is reported.

## One-shot, fresh-context policy

Every approved Phase B run is:

- one fresh, isolated model context per task ID (no shared context across
  tasks);
- exactly one attempt, with zero retries;
- given no iterative compiler or build feedback;
- given only the sanitized bundle described below — nothing about this
  repository's git history, other tasks, reference solutions, or negative
  fixtures.

## Sanitized evaluation bundle

`scripts/verify-agent-public-docs.mjs --prepare-run <output-directory> --task
<TASK-ID>` builds a self-contained, offline bundle for exactly one task: the
exact public docs, the public-doc manifest, that one task's contract, that
task's immutable input fixture, and an `INSTRUCTIONS.md` stating the output-
file boundary and the one-shot/no-hidden-tools/no-retry constraints. It
excludes Git metadata, repository source, package tests, reference/negative
fixture content, other tasks' contracts, maintainer docs, credentials, and
environment values.

Every prepared bundle is audited automatically before `--prepare-run`
returns, and the same audit is available standalone as
`scripts/verify-agent-public-docs.mjs --audit-bundle <bundle-directory>`. The
audit recursively enumerates every file in the bundle, rejects any symlink,
and fails unless the file set is exactly: the manifest-listed public docs
under `docs/`, `public-docs-manifest.json`, `task-contract.json`,
`INSTRUCTIONS.md`, and the fixed `input/` scaffold
(`package.json`, `tsconfig.json`, `vite.config.ts`, `index.html`,
`src/main.tsx`, `src/App.tsx`). No Git metadata, maintainer doc, reference/
negative fixture, other task's contract/input, run evidence, environment
file, or credential can be present without failing the audit.

The audit does not stop at filenames — it verifies exact content:

1. `public-docs-manifest.json` parses, matches the committed manifest
   field-for-field, and its own canonical `manifestContentSha256` verifies.
2. Every `docs/<manifest path>` file matches its manifest-recorded byte
   length and SHA-256 exactly.
3. `task-contract.json` is exactly one task object, its `taskId` is one of
   the fixed five, and it is canonically equal to that task's object in the
   committed contract.
4. `input/src/App.tsx` matches the task's `immutableInputFixture` byte length
   and SHA-256 exactly.
5. Every base scaffold file (`package.json`, `tsconfig.json`,
   `vite.config.ts`, `index.html`, `src/main.tsx`) matches the committed base
   fixture byte-for-byte (SHA-256 comparison).
6. `INSTRUCTIONS.md` is regenerated deterministically from the same
   `buildInstructionsText()` function `--prepare-run` used to write it, and
   compared exactly — the generator and the auditor can never silently drift
   apart because they are the same function.

It prints the task ID, public-doc manifest ID/hash, the sanitized file
inventory, and a deterministic bundle content SHA-256.

## Approval gate

Phase B does not start without explicit owner approval, in-conversation, of a
specific run record: evaluated service/model, maximum run count, exact task
IDs, retry policy, data supplied, private-repository/secret boundary,
additional spend/credit boundary, and retention boundary. Implementing this
harness, or a general request to "implement #406," is not itself that
approval. The approval summary (approver role, date, approved service/model,
maximum runs, task IDs, spend boundary, data boundary, retention boundary) is
recorded in English in
[`docs/releases/v2.9.0-agent-evaluation-report.md`](./v2.9.0-agent-evaluation-report.md)
once granted — never a private conversation transcript.

## Evidence schema

Every committed task evidence record must conform to the versioned schema
`agent-public-docs-evidence-v1`
(`validation/agent-public-docs/contracts/agent-public-docs-evidence-v1.json`).
Beyond the deterministic candidate-result fields, the schema requires the
full #402/#406 evidence-record contract: `timestamp` (ISO-8601), `ownerIssue`
(constant `"#406"`), `taskId`, `promptTaskContractId` (constant
`"agent-public-docs-v1"`), `repositoryBaselineCommit`, `phaseAHarnessCommit`,
`environment` (`os`, `arch`, `nodeVersion`, `pnpmVersion`), `toolchain`
(`react`, `reactDom`, `r3f`, `three`, `typescript`, `vite`), `packageSource`
(constant `"local packed tarball"`), `evaluatedService`,
`exactEvaluatedModelIdentifier`, `approvedRunIndex`, `filesChanged`,
`commandsExecuted`, `commandExitCodes`, `positiveAssertions`,
`negativeAssertions`, and the fields already established in the first
hardening pass. The schema also lists which fields may be `null`
(`correctedOutput`, `followUpIssue`), the seven allowed `classification`
values, and which extra field each classification conditionally requires
(for example `PACKAGE_FAILURE` requires
`packageFailureIndependentReproduction`; `DOCUMENTATION_FAILURE` requires
`documentationGap`). Validation is a small local field-presence/type
checklist in `scripts/verify-agent-public-docs.mjs` — no schema library or
runtime dependency was added. A companion run-manifest schema,
`agent-public-docs-run-manifest-v1`
(`validation/agent-public-docs/contracts/agent-public-docs-run-manifest-v1.json`),
documents the bounded `run-manifest.json` field list and the fixed
harness-artifact path set used for baseline binding (below).

`positiveAssertions`/`negativeAssertions` are a bounded, coarse observation:
each of the task contract's declared assertion strings is paired with a
single boolean tied to the task's overall `fullPass` result (`satisfied`/
`violated`). This is not a claim that each individual assertion was checked
in isolation — see [Static assertion boundaries] in the task contract for the
actual bounded checks that determine `fullPass`.

`environment` and `toolchain` are derived, not supplied blind:
`os`/`arch` come from `process.platform`/`process.arch`, `nodeVersion` from
`process.version`, `pnpmVersion` from the repository's pinned
`packageManager` field in the root `package.json` (never an unpinned global
assumption), and `toolchain` from the exact versions actually installed in
the isolated consumer — all replayed and compared, not merely present-checked
(see Complete evidence replay). `evaluatedService`,
`exactEvaluatedModelIdentifier`, `approvedRunIndex`, and `timestamp` cannot
be re-derived from candidate source — they are supplied by the approved
external run and validated structurally and against `run-manifest.json`'s
`approval` record instead: `evaluatedService` must equal
`approval.approvedService`; `exactEvaluatedModelIdentifier` must be
non-empty and compatible with `approval.approvedModel` (a case-insensitive
substring match in either direction, since an approval may record a model
family rather than an exact build identifier); `approvedRunIndex` must be a
positive integer, unique across all task evidence records in the same run,
and at most `approval.maxRunCount`; `timestamp` must parse as a valid date.

## Public-doc manifest content hash

`validation/agent-public-docs/public-docs-manifest.json` carries
`manifestContentSha256`: a canonical SHA-256 over `{manifestId,
contractVersion, baselineCommit, files: [{path, byteLength, sha256}, ...
sorted by path]}` (the hash field itself excluded from what is hashed). It is
recomputed and checked on every `pnpm consumer:agent:verify` run, included in
every prepared bundle (via the copied manifest file), required in every
run-manifest and evidence record (`publicDocManifestHash`), and printed in
the verifier's evidence summary.

## Complete evidence replay

For every committed task run, `evaluateCommittedRuns()` re-derives — from the
raw candidate files, a fresh isolated consumer install, and Git object reads,
never from the committed evidence itself — and field-by-field compares:
`contractVersion`, `promptTaskContractId`, `ownerIssue`, `packageSource`,
`repositoryBaselineCommit`, `environment`, `toolchain` (checked against the
exact consumer tuple recorded in the task contract), `phaseAHarnessCommit`
(checked against the run's own `run-manifest.json`), `packageName`/
`packageVersion`, `tarballFilename`/`tarballSha256`,
`publicDocManifestId`/`publicDocManifestHash`, the raw output file list with
per-file SHA-256 (`rawFiles`), `filesChanged`, `publicApisUsed`,
`moduleSpecifiersUsed`, `commandsExecuted` (the exact deterministic verifier
commands run — `tsc --noEmit`, and `vite build` only when typecheck
succeeded), `commandExitCodes`, the task-specific `violations` list,
`typecheckExitCode`, `buildExitCode` (an explicit `"not-run"` value when
typecheck fails, so a skipped build is never confused with a passing one),
the eight `criteria` with pass/fail, `hardGates`, the numeric `score`
(passed/total applicable criteria), `fullPass`, `warnings` (normalized:
consumer-directory absolute paths and timing numbers are replaced with
placeholders before comparison, and an empty observed warning set requires
an empty committed one), `positiveAssertions`/`negativeAssertions`, and the
derived finding groups (`unnecessaryDependencies`, `inventedApiFindings`,
`boundaryFindings`, `scopeFindings`). Each mismatch raises a focused error
naming the field and both the observed and committed values. `classification`
is not replayed against a computed value — see Classification consistency
rules below — but every field that classification legitimately depends on
is. `evaluatedService`, `exactEvaluatedModelIdentifier`, `approvedRunIndex`,
and `timestamp` are validated structurally against `run-manifest.json`
instead of replayed, since they originate from the approved external run and
cannot be re-derived from candidate source (see Evidence schema above).

## Recursive output-scope enforcement

`checkOutputFileScope()` recursively enumerates every file under a
`REFERENCE` output, `HARNESS_NEGATIVE` fixture, or raw/corrected run output
directory (rejecting any symlink outright), normalizes paths to forward-slash
form, maps a bare `App.tsx` at the fixture root to `src/App.tsx` only for the
legacy flat fixture layout (real run outputs already mirror their true
relative path), rejects duplicate normalized paths
(`duplicate-output-path`), and compares the result against the task's exact
`allowedOutputFiles`. Any unexpected file is reported as
`forbidden-file-changed`; a required allowed file that is absent is reported
as `missing-allowed-output-file`. The `nested-forbidden-file` negative
fixture (`validation/agent-public-docs/negative/nested-forbidden-file/`)
proves this recursively: it pairs a valid `App.tsx` with an unrelated nested
`src/helper.ts` and must fail with `forbidden-file-changed`.

## Run-manifest and approval-record validation

`validateRunManifest()` enforces a bounded schema (`agent-public-docs-run-manifest-v1`)
on every committed `run-manifest.json`: run ID matching its directory name,
contract version, repository baseline commit (must exactly equal the public-
doc manifest's `baselineCommit` — see baseline binding below), Phase A
harness commit, `phaseAHarnessArtifacts` (a non-empty `files` array of
`{path, sha256}` plus an `aggregateSha256`), public-doc manifest ID/hash, and
a nested `approval` record with approver role, approval timestamp, approved
service/tool, approved model identifier or family, `maxRunCount` (integer,
1-5), the exact approved task IDs (no duplicates, all from the fixed five),
`retryCount` (must be `0`), `iterativeFeedback` (must be `"none"`/`false`),
supplied-data/private-repository-data/secrets/spend/retention boundaries, and
`actualRunCount`. `actualRunCount` must not exceed `maxRunCount`; every
on-disk task directory under a run must be one of the approved task IDs (an
unapproved directory fails immediately); and the number of on-disk task
directories must equal the declared `actualRunCount`.

## Repository and Phase A harness baseline binding

A committed run cannot reference an arbitrary or unrelated commit.
`assertHarnessBaselineBinding()` proves, using only Git commands and Git
object reads (never the working tree, so a locally dirty checkout cannot
influence the result):

1. `repositoryBaselineCommit` is already forced to exactly equal the public-
   doc manifest's `baselineCommit` by `validateRunManifest()`, and that value
   is already proven to resolve to a real commit in stage 2.
2. `phaseAHarnessCommit` resolves to a real commit (`git cat-file -e`).
3. `phaseAHarnessCommit` is an ancestor of the current branch HEAD
   (`git merge-base --is-ancestor`).
4. The nine fixed harness-defining artifacts — `scripts/verify-agent-public-docs.mjs`,
   `validation/agent-public-docs/contracts/agent-public-docs-v1.json`,
   `validation/agent-public-docs/contracts/agent-public-docs-evidence-v1.json`,
   `validation/agent-public-docs/public-docs-manifest.json`,
   `docs/releases/v2.9.0-agent-evaluation-protocol.md`, and the full recursive
   contents of `validation/agent-public-docs/base/`, `tasks/`, `reference/`,
   and `negative/` — are read at `phaseAHarnessCommit` via `git show
<commit>:<path>` / `git ls-tree -r <commit>`, hashed, and compared against
   the run-manifest's declared `phaseAHarnessArtifacts` (proves the manifest
   is not lying about what existed at that commit; a file the manifest lists
   that does not exist at that commit fails immediately).
5. The same artifact set is recomputed at the current HEAD (same Git-object
   mechanism) and compared byte-for-byte against the set recomputed at
   `phaseAHarnessCommit`. Any difference — a changed, added, or removed
   harness-defining file since the commit the run claims to be bound to —
   fails. `validation/agent-public-docs/runs/**` and
   `docs/releases/v2.9.0-agent-evaluation-report.md` are intentionally excluded
   from the fixed artifact set, since those are exactly where Phase B evidence
   and its report are expected to change after approval.

Because no synthetic commit can be inserted into an existing branch's real
ancestor chain without rewriting history (which this harness never does), the
"unrelated existing commit" self-test proof uses a real, safely unreferenced
orphan commit object (`git commit-tree`, no parent, reusing HEAD's own tree)
that exists in the repository's object database but is provably not an
ancestor of HEAD, and is never pointed to by any branch, tag, or push.

## Raw/corrected output separation

A committed task's `humanCorrectionCount` must equal the length of its
`humanCorrections` array, and each entry must carry a non-empty description.
When the count is `0`, no `corrected/` directory and no `correctedOutput`
claim may be present. When the count is greater than `0`, a `corrected/`
directory is required, its file scope is checked with the same recursive
enforcement as the raw output, its `src/App.tsx` is independently typechecked
and built, it must achieve a full deterministic pass, and its recursive
file-hash list is compared against the committed `correctedOutput.files`
record. The raw output is never overwritten or mutated by this process.

## Classification consistency rules

`assertClassificationConsistency()` enforces the following before a
classification is accepted as consistent with observation (final judgment on
_which_ non-`VERIFIED` classification applies remains human-reviewed):

1. Raw output achieves a full pass → classification must be `VERIFIED`,
   `humanCorrectionCount` must be `0`, and no corrected output may be
   present.
2. Raw output does not achieve a full pass → classification must not be
   `VERIFIED`.
3. `AGENT_FAILURE` is rejected if it carries independent package-failure
   reproduction evidence or a documentation-gap record (those belong to
   `PACKAGE_FAILURE`/`DOCUMENTATION_FAILURE`), and if human corrections are
   claimed without a corrected-output record.
4. `DOCUMENTATION_FAILURE` requires a non-empty `documentationGap` record
   (exact supplied doc paths, exact missing/ambiguous guidance),
   `followUpIssue` exactly `"#407"`, and a corrected output that
   deterministically passes.
5. `PACKAGE_FAILURE` requires a `packageFailureIndependentReproduction`
   record (`stage`, `command`, `reproducedWithoutAgent: true`); absent that,
   the run must stop for reviewer handling rather than being committed.
6. `HARNESS_FAILURE` is rejected outright in any run committed after a
   successful reference/negative harness self-check in the same
   `pnpm consumer:agent:verify` invocation — the two are structurally
   inconsistent.
7. `ENVIRONMENT_FAILURE` requires an `environmentFailure` record naming the
   exact failed stage and a sanitized error; it cannot claim task-level
   verification (enforced via rule 2).
8. `MIXED_OR_UNRESOLVED` requires a non-empty `reviewerRationale` and, like
   every non-`VERIFIED` classification, cannot be a silent pass (rule 2).

## Deterministic evidence behavior

Every approved run's raw candidate files are preserved exactly (only paths/
metadata are sanitized, never code) under
`validation/agent-public-docs/runs/<run-id>/<TASK-ID>/raw/`.
`pnpm consumer:agent:verify` re-derives every field above from the raw files
on every run and fails if it disagrees with the committed evidence record —
including a changed classification, a changed criterion, a changed exit
code, a changed human-correction count, a corrected-output claim with no
corrected files, a nested unexpected file, an unapproved task directory, a
run count above the approved maximum, a manifest-hash mismatch, a
repository-baseline mismatch, a nonexistent or unrelated Phase A harness
commit, a tampered harness artifact hash, or a harness-defining file that
drifted since the approved commit — so evidence cannot silently drift from,
or be falsified relative to, what the harness actually observes, and cannot
reference a baseline the harness did not actually approve.

`node scripts/verify-agent-public-docs.mjs --self-test` is a built-in
deterministic test mode that builds one valid synthetic run entirely under
the OS temp directory, proves it is accepted, then proves twenty-one total
scenarios: the nine original evidence-tamper scenarios, five baseline-binding
tamper scenarios (repository-baseline mismatch, nonexistent harness commit,
unrelated existing harness commit, tampered harness artifact hash, and a
harness commit whose artifacts have since changed), a valid-bundle baseline,
and five bundle-content tamper scenarios (a public guide, `task-contract.json`,
`input/src/App.tsx`, `input/package.json`, and `INSTRUCTIONS.md`, each with a
single appended byte). It never writes under
`validation/agent-public-docs/runs/`; the "unrelated commit" scenario creates
one safely unreferenced orphan Git commit object (see baseline binding above)
that is never pointed to by any branch, tag, or push.
