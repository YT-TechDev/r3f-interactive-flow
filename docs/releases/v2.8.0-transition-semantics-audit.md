## 3. Current public snapshot

The initial public snapshot is:

```text
phase: initial phase
phaseIndex: initial index
progress: 0
direction: "none"
isTransitioning: false
isLocked: false
```

`FlowSnapshot` includes only `phase`, `phaseIndex`, `progress`, `direction`, `isTransitioning`, and `isLocked`. `useFlow` exposes those fields plus controls. `useFlowFrame` exposes `phase`, `phaseIndex`, `progress`, `direction`, and `isTransitioning` to Canvas-bound callbacks. `isSettling` is an internal machine signal used by the provider clock and is not part of `FlowSnapshot`, `useFlow`, or `useFlowFrame`.

The public package surface remains root-only. Public transition option types are exported intentionally; internal machine and context details are not public APIs.

## 4. Transition lifecycle

### Accepted navigation with positive duration

Immediately after an accepted `next()`, `prev()`, or `goTo()` with positive duration:

- `phase` and `phaseIndex` change immediately to the accepted target;
- `progress` resets to `0`;
- `direction` is derived from target index versus source index;
- `isTransitioning` becomes `true`;
- the source phase selects transition options;
- the source phase is not retained in the public snapshot.

Therefore, `phase` represents the accepted target during transition. The package does not expose a public source-phase field during the transition.

### Active transition

During `update(deltaMs)`:

- finite negative delta is treated as `0`;
- non-finite delta throws;
- raw elapsed progress is clamped to `[0, 1]`;
- easing receives raw progress;
- current `clamp01` behavior is applied to easing output;
- raw progress, not eased output, decides completion;
- direction remains active until raw completion;
- `isTransitioning` remains true until raw completion.

Eased output may reach `0` or `1` before raw completion without ending the transition. Non-finite or non-monotonic easing output should not be silently promoted to a stable guarantee. Current evidence supports the clamping path for ordinary finite easing output, while non-finite and non-monotonic easing edges remain classified as unresolved implementation evidence for #398 unless reproduced and contracted there.

### Completion

At raw completion:

- `progress` is forced to `1`;
- `direction` becomes `"none"`;
- `isTransitioning` becomes `false`;
- provider cooldown starts;
- the completed public snapshot remains stable during cooldown-only time.

An oversized delta consumes remaining transition time first, then applies the leftover delta to cooldown.

## 5. Navigation acceptance and rejection

Accepted navigation requires an in-bounds target different from the current phase while the machine is not manually locked, not transitioning, and not in provider cooldown.

Valid navigation is rejected without snapshot mutation when:

- `next` or `prev` is out of bounds;
- target equals current phase;
- manual lock is active;
- a transition is active;
- provider cooldown remains.

Same-phase and boundary requests do not start transition or cooldown.

Unknown `goTo()` targets throw without snapshot mutation. Unknown-target validation occurs before the normal rejection path, including while locked or transitioning. This means an invalid `goTo()` target throws even in states where a valid target would otherwise be rejected.

Navigation matrix:

| Request                                             | Current state                            | Result             |
| --------------------------------------------------- | ---------------------------------------- | ------------------ |
| In-bounds `next`, `prev`, or different-phase `goTo` | idle, unlocked, no cooldown              | accepted           |
| Boundary `next` or `prev`                           | any snapshot                             | rejected no-op     |
| Same-phase `goTo`                                   | any snapshot with known target           | rejected no-op     |
| Known different target                              | locked                                   | rejected no-op     |
| Known different target                              | active transition                        | rejected no-op     |
| Known different target                              | provider cooldown                        | rejected no-op     |
| Unknown `goTo` target                               | idle, locked, transitioning, or cooldown | throw, no mutation |

## 6. `transition.byPhase` and option precedence

Transition options resolve per field with this precedence:

```text
transition.byPhase[sourcePhase]
transition global field
legacy top-level field
default
```

Defaults:

```text
duration: 1000ms
cooldown: 0ms
easing: linear
```

`transition.byPhase` resolves from the source phase for adjacent and non-adjacent navigation. Partial overrides fall back independently per field, so a source-phase override for `duration` does not implicitly override `cooldown` or `easing`.

## 7. Easing and progress semantics

`progress` is normalized to `[0, 1]`. During positive-duration transitions, raw elapsed progress is calculated from elapsed transition time and duration. The easing function receives that raw progress. The easing output is then passed through the current `clamp01` behavior before becoming the public `progress`, except completion forces `progress` to `1`.

Completion is decided by raw elapsed progress, not by eased public progress. Easing output that reaches `1` early does not complete the transition early, and easing output that reaches `0` during an active transition does not reset lifecycle state. Direction and `isTransitioning` remain active until raw completion.

Classification:

- **Verified contract:** finite delta handling, negative-delta zeroing, raw-progress completion, public progress clamping for ordinary finite easing output, and forced completion progress.
- **Incidental implementation detail:** exact `clamp01` behavior for non-finite easing output unless #398 records deterministic evidence and compatibility impact.
- **Test coverage gap:** non-monotonic easing output and eased output reaching `0` or `1` before raw completion need explicit downstream evidence before documentation or API decisions rely on them.

## 8. Zero-duration, cooldown, and lock composition

For an accepted zero-duration transition:

- target phase and index update immediately;
- progress becomes `1`;
- direction returns to `"none"` in the same call;
- `isTransitioning` remains `false`;
- cooldown starts immediately;
- internal `isSettling` may remain true while cooldown remains.

Manual lock:

- blocks new valid navigation;
- does not pause or cancel active transition;
- does not pause provider cooldown;
- remains set through completion until `unlock()`;
- is independent from transition and settling state.

Provider cooldown belongs to the flow machine and provider clock. Hook-local input cooldowns are separate input-throttling concerns and must not be conflated with provider cooldown. Provider cooldown can reject navigation while the public snapshot remains completed and stable.

## 9. React and R3F observation boundaries

- `FlowProvider` creates one machine for its mounted lifetime.
- Provider configuration is mount-scoped.
- The provider owns the only machine-advancing RAF loop.
- Navigation synchronizes discrete React state and starts the clock.
- React snapshots update on transition frames, including completion.
- Cooldown-only frames avoid React state updates.
- `useFlowFrame` never advances the machine.
- `useFlowFrame` samples the machine from the R3F render loop.
- Multiple consumers observe one provider-owned machine.
- React and R3F sampling are not promised at the exact same instant.
- No public clock, cooldown-remaining, or settling API is implied.

Internal machine/context APIs must not be described as public. The public React surface is `FlowProvider`, `useFlow`, and `useFlowProgress`; the public R3F bridge is `useFlowFrame` inside Canvas-bound components.

## 10. Adjacent and non-adjacent usage

Adjacent navigation moves one index through `next()` or `prev()`. Non-adjacent navigation uses `goTo()` to target any known phase directly.

Forward non-adjacent example:

```text
phases: ["intro", "overview", "detail", "contact"]
current: "intro" (index 0)
goTo("contact")
accepted target: "contact" (index 3)
direction: "next"
```

Reverse non-adjacent example:

```text
phases: ["intro", "overview", "detail", "contact"]
current: "contact" (index 3)
goTo("overview")
accepted target: "overview" (index 1)
direction: "prev"
```

For adjacent and non-adjacent navigation:

- direction is based on relative indexes;
- one transition spans the direct navigation;
- intermediate phases are not visited or queued;
- `byPhase` resolves from the source;
- no route-pair, graph, queue, interruption, or timeline behavior exists;
- target phase is exposed immediately and source phase is not exposed.

This audit does not decide #399.

## 11. Application-owned alternatives

Current application-owned alternatives are:

- capture the current phase before calling navigation;
- retain the previous observed phase in application state or a ref;
- derive target from the accepted snapshot;
- maintain application-specific visual state outside the package;
- use direction when only forward/reverse distinction is needed.

Limits:

- input hooks expose no general accepted-navigation callback;
- public snapshot does not preserve source phase;
- app tracking must distinguish accepted changes from rejected requests;
- sufficiency for common non-adjacent scene transitions is decided in #399 after #396-#398.

Allowed classifications for downstream work are only:


Current classification from this audit:

- **Verified contract:** initial snapshot shape; accepted target timing; rejection stability; unknown-target throwing before normal rejection; source-phase option resolution; positive-duration lifecycle; zero-duration lifecycle; provider-owned clock; read-only R3F sampling; lock independence.
- **Documentation ambiguity:** user-facing docs do not yet spell out every target-during-transition, source-phase `byPhase`, non-adjacent, easing, zero-duration, cooldown, and lock composition detail. This is not an API defect.
- **Test coverage gap:** downstream tests should strengthen before/after snapshots, non-adjacent behavior, option precedence, easing edges, delta overflow, zero duration, lock composition, provider React snapshots, and R3F read-only sampling.
- **Incidental implementation detail:** internal `isSettling`, cooldown remaining, RAF bookkeeping, internal contexts, and unresolved non-finite/non-monotonic easing edge behavior.
- **Reproduced runtime defect:** none recorded by #395. A defect requires exact reproduction, expected contract, observed result, source/test location, and compatibility impact.
- **Genuine missing capability:** none established by #395. A hypothetical source/target metadata use case is not enough.
- **Out of scope:** runtime fixes, tests, public docs, API additions, release automation, npm publishing, tags, GitHub Releases, and milestone closure.

## 15. Guardrails

Preserve:

- current public API by default;
- React-independent core;
- one provider-owned clock;
- separate React and R3F responsibilities;
- root-only exports;
- no runtime dependencies.

Do not authorize:

- source/target metadata;
- lifecycle callbacks;
- queues or interruption;
- route pairs or graphs;
- timelines or sequencing;
- controlled external phase synchronization;
- router integration;
- visual interpolation helpers;
- camera, shader, particle, or animation-framework features.
