# r3f-interactive-flow v2.9.0

### Highlights

v2.9.0 is a focused, backward-compatible minor release. `next()`, `prev()`,
and `goTo()` now synchronously report whether a requested phase navigation
was accepted, so consumers can distinguish acceptance from a known safe
rejection without comparing snapshots manually.

### Navigation result contract

```ts
next: () => boolean;
prev: () => boolean;
goTo: (phase: TPhase) => boolean;
```

- `true` means the navigation request was accepted.
- `false` means a known safe rejection.
- `true` is not transition completion — a positive-duration transition may
  still be in progress.
- Existing callers may continue to ignore the returned value.

### Safe rejection

A known request is safely rejected, returning `false` without mutating the
public snapshot, when it hits:

- a first/last phase boundary
- a same-phase `goTo()` target
- a manual lock
- an active transition
- provider cooldown

### Zero-duration and unknown targets

- An accepted zero-duration navigation returns `true` and settles
  synchronously in the same call.
- An unknown `goTo()` target continues to throw.
- Unknown-target validation remains ordered before the normal rejection
  path.

### Implementation evidence

Issue #462 approved the navigation-acceptance contract. Issue #463 tracked
the focused implementation and regression coverage. Pull Request #466 merged
the runtime behavior: the core flow machine owns the accepted/rejected
decision, `FlowProvider` forwards that same result through the public
`useFlow()` controls, and the internal input-navigation helper uses the
direct machine result instead of inferring acceptance from a snapshot
comparison. Focused core, provider, and public-type regression coverage was
added for the boundary, same-phase, lock, active-transition, cooldown,
zero-duration, and unknown-target cases.

### Documentation evidence

Issue #464 and Pull Request #467 aligned the root README, the package
README, and the core concepts guide with the merged contract: the exact
control signatures, the acceptance/rejection matrix, the ordering of
unknown-target validation ahead of the normal rejection path, and the
acceptance-versus-completion distinction.

### Compatibility and migration

- Existing callers that ignore the returned result continue to work
  unchanged.
- No migration is required.
- Public snapshots, `FlowFrameState`, `FlowProviderProps`, runtime exports,
  package subpaths, dependencies, peer dependency ranges, transition timing,
  and input semantics remain unchanged.
- No rejection-reason API or broader navigation abstraction was added.
