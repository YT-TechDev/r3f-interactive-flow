# v2.5.0 Real-world Usage Validation Contract

## Purpose and scope

This is the maintainer contract for the later v2.5.0 real-world usage validation work. It defines what Issues #378, #379, and #380 may build, validate, classify, and report for a representative multi-phase React Three Fiber consumer.

This document is not the consumer implementation. It does not authorize runtime behavior changes, public API additions, new exports, new dependencies, package version changes, release automation changes, publishing, tags, or GitHub Releases.

## Consumer location decision

The real-world consumer must be a separate, focused fixture or example rather than expanding `examples/vite-basic` into a large showcase. If the current repository still does not establish an exact directory name when #378 begins, #378 may choose one that satisfies these constraints:

- remain small and validation-focused;
- not become a portfolio template, documentation-site generator, visual-effects collection, or application starter;
- remain outside `packages/r3f-interactive-flow`;
- keep application-specific visual code in the consumer;
- import `r3f-interactive-flow` only from the public package root;
- avoid unsupported package subpaths, including `src`, `dist`, `react`, `r3f`, `input`, or other responsibility-specific paths.

## Package-consumption lanes

The validation work must keep these lanes separate. Findings must record the lane used.

| Lane                         | Package source                                                                                                                  | Purpose                                                                                                                               | Must not use                                                                                       |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Published-package lane       | The exact version resolved by `npm view r3f-interactive-flow version`. Expected to be `2.4.0` only if that command verifies it. | Validate the package as actual users receive it and identify published-package, declaration, export, peer, or documentation problems. | `workspace:*`, internal source paths, `dist` paths, symlink-only package access, package subpaths. |
| Packed-current-checkout lane | A tarball produced from the current checkout through the repository's existing build/pack workflow.                             | Validate current repository packaging before a later release and distinguish already-published behavior from repository-only changes. | `workspace:*`, internal source paths, `dist` paths, symlink-only package access, package subpaths. |

Do not conflate lanes. A behavior observed only in the packed-current-checkout lane is not evidence about the already published package. A behavior observed only in the published-package lane may already be fixed in the current checkout, but still needs explicit classification.

## Representative phase structure

Use a small but nontrivial phase sequence of five or six generic phases. Recommended names:

1. `intro`
2. `overview`
3. `detail`
4. `compare`
5. `summary`
6. `contact`

This phase set must support adjacent `next()` and `prev()` navigation, non-adjacent `goTo()`, first and last boundary rejection, visible transition progress, direction observation, and DOM UI plus Canvas scene coordination. The contract intentionally does not prescribe scene assets, camera choreography, layout, or visual polish.

## Scenario matrix

Later issues must execute and record the relevant scenarios. Synthetic automation may assist reproducibility, but synthetic wheel events must not be described as genuine high-resolution trackpad validation.

| Category                      | Scenario                                                                  | Expected ownership and result                                                                                                                              |
| ----------------------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DOM controls                  | Previous and next buttons                                                 | Adjacent navigation works through public `useFlow` controls and respects transition, lock, cooldown, and boundary behavior.                                |
| DOM controls                  | Direct `goTo()` buttons                                                   | Non-adjacent navigation works for valid phases through the public package root only.                                                                       |
| DOM controls                  | Disabled or boundary behavior                                             | First/last boundaries reject navigation without corrupting phase state. Disabled UI is application-owned but should reflect flow state accurately.         |
| DOM controls                  | DOM progress observation without `useFlowFrame`                           | `useFlowProgress` continues to update during transitions even when no Canvas consumer is mounted.                                                          |
| Canvas observation            | One `useFlowFrame` consumer                                               | A Canvas-bound observer reads phase, progress, direction, and delta without advancing the machine.                                                         |
| Canvas observation            | Multiple `useFlowFrame` consumers                                         | Multiple observers receive consistent snapshots and do not create multiple clocks.                                                                         |
| Canvas observation            | Observers do not advance the machine                                      | Flow advancement remains owned by `FlowProvider`, not Canvas consumers.                                                                                    |
| Canvas observation            | DOM progress without Canvas                                               | DOM progress continues when no Canvas consumer is mounted.                                                                                                 |
| Wheel                         | Standard mouse wheel                                                      | Accepted wheel navigation advances one adjacent phase and prevents native behavior only after accepted navigation.                                         |
| Wheel                         | Normalized delta modes                                                    | Pixel, line, and page delta modes are covered where practically reproducible.                                                                              |
| Wheel                         | High-resolution trackpad accumulation                                     | Physical-device evidence records accumulation behavior; one burst must not skip several phases. Synthetic wheel events are not physical trackpad evidence. |
| Wheel                         | Rejection states                                                          | Boundary, transition-lock, provider-cooldown, and hook-cooldown rejection preserve native browser behavior.                                                |
| Wheel                         | `preventDefault()` timing                                                 | `preventDefault()` occurs only after accepted navigation.                                                                                                  |
| Touch                         | Below-threshold gesture                                                   | Below-threshold movement does not navigate and preserves native behavior.                                                                                  |
| Touch                         | Accepted swipe                                                            | An accepted swipe navigates once in the expected direction.                                                                                                |
| Touch                         | One navigation per gesture                                                | Continued movement in one gesture does not skip several phases.                                                                                            |
| Touch                         | Interruption or cancellation                                              | Cancelled or interrupted gestures do not leave stale actionable state.                                                                                     |
| Touch                         | Ignored/actionable origin                                                 | A gesture that starts ignored remains ignored for the whole gesture; a gesture that starts actionable remains governed by that origin.                     |
| Touch                         | Unresolved explicit target ref                                            | An unresolved explicit target ref remains inactive and must not broaden to `window`.                                                                       |
| Keyboard                      | Accepted next and previous keys                                           | Configured next and previous keys navigate adjacent phases.                                                                                                |
| Keyboard                      | Focused text inputs, textareas, selects, buttons, links, editable content | Native typing, selection, activation, and editing are preserved when navigation is rejected or ignored.                                                    |
| Keyboard                      | Repeated key behavior                                                     | Relevant key-repeat behavior is recorded and does not unexpectedly skip phases during transition or cooldown rejection.                                    |
| Native and nested interaction | Nested scrollable region                                                  | Native nested scrolling is preserved when flow navigation is ignored or rejected.                                                                          |
| Native and nested interaction | Page-level native scrolling                                               | Page scrolling is preserved when no navigation is accepted.                                                                                                |
| Native and nested interaction | Actionable controls                                                       | Buttons, links, form fields, and other actionable elements keep native interaction unless accepted flow navigation explicitly owns the event.              |
| Native and nested interaction | Ignored regions                                                           | Regions configured as ignored remain ignored and preserve native browser behavior.                                                                         |
| Native and nested interaction | Rejected navigation                                                       | Rejected navigation preserves native browser behavior.                                                                                                     |
| Layout and device behavior    | Desktop viewport                                                          | Consumer layout remains usable on a representative desktop viewport; layout is application-owned.                                                          |
| Layout and device behavior    | Narrow mobile viewport                                                    | Consumer layout remains usable on a narrow viewport; the library does not provide responsive layout.                                                       |
| Layout and device behavior    | Touch-capable viewport                                                    | Touch-capable behavior is validated separately from desktop pointer behavior.                                                                              |
| Reduced motion                | Application-selected reduced transition configuration                     | The consumer may select shorter or simpler transitions for reduced motion; policy and visual treatment are shared application responsibilities.            |
| Reduced motion                | Intentional `FlowProvider` key remount                                    | Applying changed provider configuration requires an intentional React `key` remount.                                                                       |
| Reduced motion                | Library policy boundary                                                   | Do not claim the library automatically implements a full reduced-motion policy.                                                                            |

## Evidence recording requirements

For each scenario, record:

- validation lane;
- environment and browser;
- viewport or input device;
- exact action;
- expected result;
- observed result;
- pass/fail status;
- relevant evidence: command output, screenshot, video, trace, or concise notes;
- finding category;
- follow-up issue link when required.

Evidence must distinguish physical-device validation from synthetic browser automation. Do not label synthetic wheel, touch, or keyboard events as physical device proof.

## Finding taxonomy

| Category                       | Use when                                                                                                                                                                        | Classification rules                                                                                           |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Runtime defect                 | The package accepts, rejects, advances, locks, cools down, prevents default browser behavior, reports progress, reports direction, or observes frames incorrectly.              | Incorrect accepted/rejected navigation behavior in the package is a runtime defect. Application misuse is not. |
| Type problem                   | Public declaration output is missing, wrong, unusable, or inconsistent with the documented public API.                                                                          | Problems with `dist/index.d.ts`, `dist/index.d.cts`, or root-import type usability belong here.                |
| Documentation gap              | Correct behavior is not discoverable or is misleading in public docs.                                                                                                           | Documentation gaps within #380's approved scope are handled by #380.                                           |
| Application concern            | The consumer's layout, scene composition, visual polish, app-specific accessibility wiring, or app-specific reduced-motion policy needs work without exposing a package defect. | Keep these in the consumer unless evidence shows the package contract is wrong.                                |
| Out-of-scope request           | The finding asks for shaders, camera presets, timelines, router integration, new speculative APIs, visual-effect systems, templates, CLIs, or generators.                       | Do not add these to v2.5.0 automatically.                                                                      |
| Environment/tooling limitation | Evidence collection is blocked or materially limited by browser, device, network, install, or tooling constraints.                                                              | Use only when the limitation is recorded with enough detail to reproduce or understand the gap.                |

## Follow-up rules

- Confirmed runtime defects receive separate focused bug issues.
- Confirmed public type defects receive separate focused type issues.
- Documentation gaps are handled by #380 when within its approved scope.
- Application concerns stay in the consumer unless they expose a package defect.
- Out-of-scope requests are not added to v2.5.0 automatically.
- Public API additions, new exports, runtime dependencies, or architecture changes require separate owner-approved issues.
- Findings must not be silently fixed inside #378, #379, or #380 when outside those issues' contracts.

## Architecture and maintenance guardrails

- `core/` remains React-independent.
- `react/` owns provider, context, and React hooks.
- `r3f/` owns Canvas-bound frame observation.
- `input/` owns browser input handling.
- `FlowProvider` owns the only machine-advancing animation-frame clock.
- `useFlowFrame` is read-only.
- Public imports come only from `"r3f-interactive-flow"`.
- No new public API or package export is authorized.
- No runtime dependency is authorized.
- No large demo, visual-effects collection, template, router integration, CLI, or code generator is authorized.
