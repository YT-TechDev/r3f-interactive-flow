## Goals

Define a bounded evidence plan for:

- packed-package consumers (real `.tgz` installs, not workspace or source aliasing);
- framework/client boundaries (Vite consumer, Next.js App Router Client Component consumer);
- supported-peer sampling (minimum and current React/R3F/Three.js tuples);
- TypeScript/module resolution (Bundler and NodeNext, current and one lower representative compiler line);
- AI-agent integration from public documentation only (README + guides, no private context).

- Universal framework support or a promise to validate every framework.
- Every Vite, Next.js, TypeScript, React, R3F, or Three.js patch release.
- Vendor/model comparison or declaring a "best" AI model.
- Marketing benchmark claims of any kind.
- Paid or high-volume AI evaluation without explicit owner approval.
- New runtime APIs.
- New package exports or subpaths.
- Next.js tooling or AI-evaluation tooling inside the published package.
- Router integration of any kind.
- Application templates or scaffolding tools.
- Any v2.9.0 release action (version bump, changelog, tag, publish, GitHub Release, milestone close).

## Terminology and claim levels

### Supported range

The semver range intentionally declared by package metadata (`peerDependencies` in `packages/r3f-interactive-flow/package.json`). It expresses an intentional compatibility boundary. It does **not** mean every version tuple inside the range is exercised by CI or any other automated check.

### Sampled configuration

An exact version tuple exercised by a named validation command — a single point inside (or at the edge of) a supported range, chosen deliberately and pinned for reproducibility.

### Verified run

One execution tied to all of:

- repository commit;
- package version or tarball identity;
- exact tool and peer versions;
- command and result;
- environment;
- evidence artifact.

A verified run proves the sampled configuration worked at that commit, with those exact versions — nothing broader.

### Documented boundary

A supported usage rule established by public documentation, such as the Client Component / Canvas placement rules in `docs/guides/r3f-usage.md` and the package README's "Client usage and Next.js App Router boundary" section. A documented boundary is guidance, not itself a runtime guarantee enforced by the package.

### Not evaluated

The explicit inverse of the above: no compatibility or support conclusion may be inferred for anything outside a verified run, a sampled configuration, or a documented boundary.

Explicit statements this document treats as binding for all downstream Issues:

- Sampled success supports the declared peer range but does not prove every point-version in that range works.
- Next.js is a **sampled consumer boundary**, not a package peer dependency and not a blanket framework-support promise. Next.js does not appear in `dependencies`, `peerDependencies`, or `devDependencies` of the published package today, and #404 must not add it there.
- TypeScript samples are **declaration-resolution evidence** (does the compiler resolve the package's public types correctly under a given `module`/`moduleResolution` setting), not an unlimited compiler-support guarantee across every TypeScript release.
- AI-agent results are **documentation/integration evidence** — do they reveal a real package or documentation gap — not model rankings, benchmarks, or vendor comparisons.

## Version-selection rules

- Exact peer samples (`PEER-MINIMUM-SAMPLE`, `PEER-CURRENT-SAMPLE`) come from the existing live `scripts/verify-peer-compatibility.mjs` `compatibilityCases` array — never re-derived independently.
- Current versions (workspace TypeScript, current React/R3F/Three.js) come from the committed `pnpm-lock.yaml` and `package.json` manifests, not from `npm view ... latest` (note that the npm registry's `typescript@latest` is currently `7.0.2`, newer than this workspace's pinned `6.0.3` — "current" in this document always means "current in this workspace," not "current on npm").
- A lower TypeScript sample must be an exact maintained release (confirmed as published, non-prerelease, on the npm registry) and must be justified in the matrix row that uses it (see `TS-LOWER-REPRESENTATIVE` above).
- Sampled versions are pinned for reproducibility — no ranges, no floating tags, matching the existing `verify-peer-compatibility.mjs` convention of `--save-exact` pinned installs.
- Routine dependency updates (e.g. a new Three.js patch release) may update a sampled _current_ tuple through a focused PR, following the existing pattern used when `package.json`/`pnpm-lock.yaml` devDependencies move.
- Peer-_range_ expansion (changing the declared `peerDependencies` floor or ceiling) requires separate evidence and separate owner approval — it is out of scope for every Issue in this milestone.
- Matrix growth (a new row, a new sampled tuple) requires either a reproduced gap or a clearly articulated, non-redundant support value — not "more coverage" for its own sake.
- No Cartesian product across tools: the matrix intentionally pairs one minimum and one current peer tuple with a bounded set of TypeScript modes, rather than testing every peer tuple against every TypeScript mode against every bundler.

## Package-source rules

- Positive #403-#405 consumers install the actual local `.tgz` produced by the existing verified packaging path (`npm pack` from `packages/r3f-interactive-flow`, the same mechanism `scripts/verify-packed-package.mjs` and `scripts/verify-peer-compatibility.mjs` already use).
- No `workspace:*`, path alias, source import, or monorepo resolution may satisfy the package dependency in any positive consumer fixture — this mirrors the existing `assertInstalledFromTarball` checks in both existing scripts, which explicitly fail if the installed copy resolves back into the workspace source tree.
- Tarball creation reuses the existing verified packaging path; it must not be reimplemented ad hoc per downstream Issue.
- Each run records the tarball filename and, when practical, an integrity/content hash, so a given verified run can be tied back to an exact tarball.
- Peers are installed by the consumer itself (via its own `package.json`/lockfile or explicit install command), not symlinked from the workspace — this differs intentionally from `package:smoke`'s current behavior (which does symlink workspace peers for speed) and matches `package:compat`'s current behavior (which installs real, non-workspace peers per case).
- Package-private source, tests, scripts, examples, and docs must remain absent from the tarball — already enforced by the `files` allowlist (`dist`, `README.md`, `LICENSE`, `CHANGELOG.md`) and by `pnpm pack:dry-run` / `package:verify`.
- The existing published-package consumer (`validation/vite-published-package`, pinned to `2.4.0`) remains independent evidence and must not be silently repointed to a newer version during #402 or any of #403-#405; repointing it, if ever justified, is a separate decision for a separate Issue.

## AI-agent scoring contract

Use a per-task evidence score, not a vendor leaderboard.

Eight binary criteria:

1. build/typecheck succeeds;
2. required public behavior is implemented;
3. package-root imports only;
4. React Client Component boundary is correct where applicable;
5. Canvas boundary is correct where applicable;
6. no invented API or package export;
7. no unnecessary runtime dependency or framework coupling;
8. change remains inside the fixed task scope.

Hard gates (a task cannot pass when any applicable gate fails):

- build/typecheck success;
- package-root imports;
- no invented API;
- correct required Client/Canvas boundary;
- no secret/private-repository exposure.

Each run records:

- score out of applicable criteria;
- hard-gate status (pass/fail per gate);
- number and description of human corrections;
- whether the corrected output passes deterministic verification.

Explicitly prohibited: aggregating scores into a universal model ranking, declaring a best vendor or model, or comparing runs that used different task inputs or evidence contracts.

## Failure classification

### PACKAGE_FAILURE

The real packed/published package, exports, declarations, runtime outputs, peer metadata, or client directive fails under an in-matrix scenario.

### DOCUMENTATION_FAILURE

The package works, but public guidance is missing, ambiguous, or directly causes a reproducible integration mistake.

### AGENT_FAILURE

The fixed task and public documentation are sufficient, but the agent invents APIs, violates boundaries, ignores requirements, or produces non-buildable output.

### HARNESS_FAILURE

The fixture, verification script, assertion, package-install procedure, or evidence capture is incorrect.

### ENVIRONMENT_FAILURE

Registry, network, filesystem, browser installation, or hosted-runner failure prevents a valid conclusion.

### MIXED_OR_UNRESOLVED

Evidence spans categories or is insufficient. Human review is required before filing a product/docs defect.

Classification rules:

- reproduce without the AI agent before declaring `PACKAGE_FAILURE`;
- reproduce with the exact public docs before declaring `DOCUMENTATION_FAILURE`;
- validate the harness against a known-good fixture before declaring `AGENT_FAILURE`;
- do not weaken tests merely to reclassify a failure;
- #407 may change docs only for reproduced material documentation gaps;
- runtime/API changes require a separate focused Issue and owner approval — never bundled into a docs-correction PR.
