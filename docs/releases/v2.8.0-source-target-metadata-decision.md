# v2.8.0 Source and Target Transition Metadata Decision

## Status

- Decision date: 2026-07-24
- Milestone: v2.8.0 - Transition contract completeness (#22)
- Issue: #399
- Baseline main commit: `d43c4396a0e7264e82e3d81eed7b0f77e695ca0a`
- Decision status: Accepted

## Decision

r3f-interactive-flow will not add `sourcePhase`, `targetPhase`, `previousPhase`, or transition metadata fields to `FlowSnapshot`, `FlowControls`, or `FlowFrameState` in v2.8.0. This decision produces no runtime change, no public API change, no type or export change, and no migration for existing consumers.

## Question

Does the stable v2 public observation contract require minimal source/target transition metadata for predictable real non-adjacent scene transitions?

## Current observation contract

The public React surface (`FlowProvider`, `useFlow`, `useFlowProgress`) exposes `FlowSnapshot`: `phase`, `phaseIndex`, `progress`, `direction`, `isTransitioning`, `isLocked`, plus `next`, `prev`, `goTo`, `lock`, `unlock` on `FlowControls`.

The public R3F bridge (`useFlowFrame`, used inside Canvas-bound components) exposes `FlowFrameState`: `phase`, `phaseIndex`, `progress`, `direction`, `isTransitioning`. It samples the same provider-owned machine read-only and never advances it.

Internal `isSettling`, cooldown remaining, internal machine/context APIs, and RAF bookkeeping are not part of either public surface.

## Concrete non-adjacent scenario

Using phases `["intro", "overview", "detail", "contact"]`, as proven in `FlowProvider.test.tsx`:

- `intro -> contact` via `goTo("contact")`: accepted target `phase` becomes `"contact"` immediately, `direction` is `"next"`.
- `contact -> overview` via `goTo("overview")` after the forward transition completes: accepted target `phase` becomes `"overview"` immediately, `direction` is `"prev"`.
- Accepted target timing: `phase` and `phaseIndex` update to the target synchronously with the accepted call; `progress` resets to `0` for a positive-duration transition.
- Rejected request stability: a `goTo` call issued during an active transition does not change the observed phase or the application-derived trace.
- Same-phase stability: a `goTo` call targeting the current phase does not change the observed phase or the application-derived trace.

## Application-owned derivation

The evidence-backed pattern, demonstrated in `FlowProvider.test.tsx` using only public `useFlow` and ordinary React state/ref APIs:

- store the previously observed public `phase` in a ref;
- on render, compare the ref against the current public `phase`;
- when the phase has actually changed, treat the ref value as `source` and the current `phase` as `target`, then update the ref;
- use the current public `direction` as the accepted direction during a positive-duration transition;
- for a zero-duration transition, where `direction` returns to `"none"` in the same call, derive direction from the phase indexes of the previous and new phase instead;
- a rejected request produces no phase change, so the derivation never records a false trace;
- a same-phase request produces no phase change, so the derivation never records a false trace.

This pattern is illustrative evidence of sufficiency, not a package API. No reusable helper is added to the library for this.

## Lifecycle analysis

| State                             | Source/target derivable from public API?                                                                                                         | New public field required? |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------- |
| Initial state                     | Yes — no prior phase exists; application trace starts `null`                                                                                     | No                         |
| Accepted positive-duration start  | Yes — previous ref value is source, new `phase` is target, `direction` set                                                                       | No                         |
| Active transition                 | Yes — source/target already captured at the accepted-start observation                                                                           | No                         |
| Completion                        | Yes — trace remains stable; `direction` returns to `"none"` at completion                                                                        | No                         |
| Zero-duration accepted transition | Yes — previous/new phase observation still yields source/target; direction derivable from indexes since `direction` is `"none"` in the same call | No                         |
| Known rejected navigation         | Yes — no phase change occurs, so no false trace is recorded                                                                                      | No                         |
| Manual lock                       | Yes — lock blocks new navigation; existing trace is unaffected                                                                                   | No                         |
| Provider cooldown                 | Yes — cooldown-only frames do not mutate the completed public snapshot, so the trace remains stable                                              | No                         |

## React impact

Public `phase` (and `phaseIndex`) change synchronously with an accepted navigation call, before any transition frame runs. This gives application code a reliable point to compare against a previously retained phase. The demonstrated application-owned previous-phase pattern is sufficient for the non-adjacent scenario proven in #397. Rejected requests and same-phase requests do not mutate the public snapshot, so they cannot create a false trace. Adding `sourcePhase`/`targetPhase`/`previousPhase` to `FlowSnapshot` or `FlowControls` would permanently expand the stable React surface without solving a case the current pattern cannot already solve.

## R3F impact

`useFlowFrame` samples the same provider-owned machine read-only, once per R3F frame. A Canvas-bound component may retain the previously sampled `phase` in a ref and apply the same derivation pattern used in React to obtain source and target for the demonstrated scenario. The library does not promise that React state updates and R3F frame sampling occur at the exact same instant; they observe the same underlying machine but through separate scheduling paths (React commits versus the R3F render loop). Source/target metadata, even if added, would not by itself solve application-specific interpolation, asset ownership, or visual state — those remain application concerns regardless of what the snapshot contains.

## Type and compatibility impact

An additive optional field on `FlowSnapshot`, `FlowControls`, or `FlowFrameState` would be source-compatible for most existing TypeScript consumers (structural typing permits extra properties to be ignored). However, it would still:

- expand `FlowSnapshot` and by extension `FlowControls` (which extends it), requiring every snapshot-shape assertion across the test suite to account for the new field;
- expand `FlowFrameState`, requiring the same for R3F-facing tests;
- require regenerating both the ESM (`dist/index.d.ts`) and CommonJS (`dist/index.d.cts`) declaration outputs and re-verifying they stay in sync;
- add a permanent semantic obligation: once source/target metadata is public, its lifecycle (initial, active, completed, zero-duration, rejected, locked, cooldown) becomes part of the stable v2 contract that must be documented and preserved for the remainder of v2;
- require documentation and migration guidance even though no code path strictly requires it;
- expand long-term compatibility and test-maintenance surface for a capability that current public APIs and application-owned state already provide.

The addition is therefore rejected primarily on contract-expansion cost, not on any TypeScript compatibility break.

## Alternatives considered

1. Keep the current API plus documentation — accepted.
2. Application-owned previous-phase tracking — accepted for application-specific visual state; proven sufficient by #397 evidence.
3. Add `sourcePhase` only — rejected for v2.8.0; no demonstrated case where application-owned tracking cannot derive it.
4. Add `targetPhase` only — rejected because `phase` already is the accepted target immediately after an accepted navigation call.
5. Add both source and target — rejected as unnecessary contract expansion given items 3 and 4.
6. Add accepted-navigation callbacks or event emitters — rejected; public phase observation on change already supplies accepted-state evidence, and this expands the API surface beyond a single field.
7. Add route-pair configuration, queues, graphs, timelines, or interruption — rejected and out of scope for this issue and this milestone.

## Why no new capability is required

`phase` already exposes the accepted target immediately, `phaseIndex` identifies the target index, and `direction` identifies forward or reverse movement for positive-duration transitions. The #397 evidence in `FlowProvider.test.tsx` demonstrates that application code retaining the previously observed public phase in a ref, and updating a derived trace only when the observed phase actually changes, correctly derives `source`, `target`, and `direction` for forward non-adjacent (`intro -> contact`), reverse non-adjacent (`contact -> overview`), rejected, and same-phase requests, using no package API addition. The #398 evidence confirms this reasoning extends to zero-duration transitions, where direction can be derived from source/target indexes, and to lock/cooldown composition, where the completed public snapshot remains stable. No concrete common use case in the real usage consumer or the completed test evidence fails deterministically with the current public API.

Classification: No genuine missing capability demonstrated.

## Future reconsideration threshold

A future v2 minor or v3 planning cycle may reconsider this decision only when all of the following are presented together:

- a concrete common integration that the current public API cannot serve;
- deterministic failure reproduced against current public APIs;
- proof that previous-phase observation (React and R3F) is insufficient for that integration;
- exact lifecycle semantics for the proposed field across initial, active, completed, zero-duration, rejected, locked, and cooldown states;
- a full compatibility analysis across `FlowSnapshot`, `FlowControls`, `FlowFrameState`, and both declaration outputs;
- a separately approved, focused Issue.

This document does not promise a v3 change and does not reserve a field name.
