# v2.7.0 Accessibility Responsibility Contract

## Purpose and scope

This is the maintainer contract for the v2.7.0 accessibility and reduced-motion guidance work. It defines what `r3f-interactive-flow` guarantees, what consuming applications remain responsible for, how reduced-motion configuration is integrated through existing APIs, how later Issues #390, #383, #391, #392, #393, and #394 own evidence, and when a runtime change may be proposed.

This is contract documentation only. It does not change runtime source, tests, the validation consumer, examples, README files, user guides, package version, changelog, dependencies, CI, public API, type declarations, exports, peer ranges, package boundaries, publishing, tags, GitHub Releases, milestones, or Issue state. It does not close, implement, or silently rescope #383.

Accessibility concepts such as keyboard-operable application functionality, focus visibility and order, reduced-motion user preferences, and application-owned status messages are used only as contextual framing. This contract does not claim WCAG conformance, screen-reader certification, browser or assistive-technology certification, formal accessibility compliance, or that the package alone can make an application accessible.

## Package responsibility

`r3f-interactive-flow` is responsible for:

- predictable phase state and typed navigation through `next`, `prev`, and `goTo`;
- deterministic transition progress, direction, lock, transition, and cooldown behavior;
- exposing React controls and state so applications can render their own DOM controls and status UI;
- preserving current native-control and editable-target protections in optional input hooks;
- leaving rejected navigation unprevented;
- preventing default only for accepted navigation when configured, plus the documented committed-touch continuation behavior;
- ignoring repeated keyboard events according to the current hook contract;
- respecting `ignoreWhenTyping` according to the current hook contract;
- allowing zero-duration or short-duration transition configuration through existing provider options;
- cleaning up provider-owned `requestAnimationFrame` work when a provider instance unmounts;
- keeping browser input hooks optional.

The package is not responsible for rendering accessible UI.

## Application responsibility

Consuming applications remain responsible for:

- rendering visible DOM navigation controls;
- using appropriate native elements, labels, names, disabled states, and semantics;
- ensuring the complete flow remains operable without relying exclusively on wheel, touch, or package keyboard shortcuts;
- focus order, visible focus styling, avoiding obscured focus, deciding whether and when focus moves after a phase change, and restoring focus after intentional remounts;
- ARIA attributes, phase announcements, status messages, screen-reader wording, visual contrast, target size, layout, and responsive behavior;
- nested-scroll layout and CSS;
- `touch-action`, overscroll, and native-scrolling policy;
- detecting `prefers-reduced-motion` or exposing an application preference;
- selecting normal and reduced transition configurations;
- applying reduced-motion policy to scene animation, camera movement, parallax, shaders, particles, CSS motion, and other visual effects;
- deciding whether provider state reset on intentional remount is acceptable.

No package API may be implied for any of these responsibilities.

## Visible controls and alternative operation

The approved application pattern is to use `useFlow()` to render normal DOM buttons or links owned by the application. Previous and Next controls should reflect first and last phase boundaries through application-owned disabled states. Direct phase controls may reflect the current phase as disabled or otherwise expose current state using application-owned semantics.

Visible DOM controls are the baseline alternative to wheel, swipe, or shortcut navigation. Optional input hooks are enhancements, not the only way to operate the flow. The library must not render buttons or other controls on the application's behalf and this contract does not prescribe a design system.

## Keyboard and native activation contract

There are two supported paths.

### Native DOM control path

Native buttons and links use browser activation behavior. The application owns their semantics and focus behavior. The flow can remain keyboard-operable through these controls even when `useKeyboardInput` is not mounted.

### Optional keyboard-hook path

Configured navigation keys may navigate when the target is not protected. Repeated keydown events remain ignored according to the current contract. Typing and editable targets remain protected when `ignoreWhenTyping` is true. Space and Enter on actionable controls retain native activation behavior. Rejected navigation remains unprevented. Accepted navigation is prevented only when configured.

The package does not implement roving tabindex, focus traps, focus movement between phases, application-wide shortcut registration, keyboard shortcut announcements, or assistive-technology certification.

## Focus contract

Phase navigation does not move DOM focus. `FlowProvider`, `useFlow`, and the input hooks do not own focus. Intentional provider remount may remove and recreate descendant DOM, so the application must decide how focus should be preserved or restored. Focus order, visible focus, focus restoration, and focus announcement remain application responsibilities.

Later tests may verify that the library does not unexpectedly interfere with focus, but they must not turn that into automatic package-owned focus behavior.

## Approved reduced-motion pattern

The approved pattern uses existing APIs only. The application:

1. determines a motion preference through application state, a user setting, or its own `prefers-reduced-motion` integration;
2. selects normal and reduced provider transition configuration;
3. changes the React `key` on `FlowProvider` when the mounted provider must receive the new configuration;
4. accepts that this intentionally unmounts the old provider and creates a new flow machine;
5. separately applies the motion preference to Canvas and non-Canvas visual effects.

Provider configuration is mount-scoped. Changing configuration props on the same provider position does not reconfigure the existing machine. `key` is React's remount mechanism, not a public `FlowProvider` prop. Provider remount resets phase, transition, lock, progress, and cooldown state to the new provider's initial configuration. Stale provider-owned `requestAnimationFrame` work must not survive unmount.

`duration: 0` is supported for immediate transitions. A short non-zero duration is also valid. Provider cooldown is a separate application configuration decision and may remain positive even when transition duration is zero. The application must decide whether an immediate transition or a shorter, simpler transition is appropriate; `duration: 0` is not the universal accessibility answer.

The package does not read `matchMedia`, expose a reduced-motion hook, own a media-query subscription, preserve flow state across intentional provider remount, or automatically reduce scene, camera, shader, particle, CSS, or other visual motion.

## Scene-motion boundary

Reducing provider transition duration does not automatically reduce every visual update driven by `useFlowFrame`. Application scene code must use the selected motion preference to reduce, replace, or remove non-essential movement. The package does not decide which visual motion is essential.

Scene motion must remain in Canvas-bound components and refs, not per-frame React state. No animation framework, camera preset, shader, visual-effects, or particle API is authorized.

## Phase status and announcements

`useFlow()` and `useFlowProgress()` expose enough React state for application-owned visible status and announcement patterns. The application may use ordinary text, `role="status"`, `aria-live`, or another application-appropriate pattern.

The library must not automatically announce every frame of transition progress. Announcements should normally use meaningful discrete phase state rather than chatty per-frame progress updates. Exact announcement wording and frequency remain application decisions. No new ARIA or live-region API is authorized.

## Touch, wheel, scroll, and mobile boundaries

Rejected wheel, touch, and keyboard navigation preserves native behavior. Accepted navigation may prevent default only according to the current hook configuration. Ignored and nested-scroll regions remain application-selected through existing selectors and CSS. Touch support remains a bounded single-touch swipe helper, not a gesture framework.

Visible DOM controls must remain available as the non-gesture path. Layout, target size, `touch-action`, overscroll behavior, and mobile usability remain application responsibilities. No broad browser, physical-device, or accessibility certification is claimed.

## Architecture and API guardrails

- Core logic remains React-independent.
- React Context and hooks remain in the React layer.
- R3F hooks remain Canvas-bound.
- DOM input logic remains separate from scene logic.
- No React state is introduced for per-frame scene values.
- No browser globals are accessed at module import time.
- Public imports remain package-root only.
- No new public API or package subpath is authorized.
- No runtime dependency is authorized.
- React, React DOM, Three.js, and React Three Fiber remain peer dependencies.
- No package-owned UI, focus manager, ARIA manager, announcement system, media-query hook, gesture framework, animation framework, or design system is authorized.

## Runtime-change conditions

A runtime change may be proposed only when later evidence reproduces a current package behavior that contradicts the existing accepted/rejected navigation, lifecycle, target, timing, cleanup, native-control, or public API contract. The proposal must stay focused, preserve backward compatibility unless separately approved, include regression coverage, and document why application-owned accessibility integration is insufficient.

Runtime changes are not authorized merely because an application needs visible controls, focus styling, ARIA wording, a reduced-motion preference UI, media-query wiring, status text, layout changes, touch target changes, scene-motion changes, cross-browser claims, physical-device claims, screen-reader claims, or certification.
