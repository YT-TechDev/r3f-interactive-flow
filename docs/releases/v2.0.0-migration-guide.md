# v2.0.0 Migration Guide

## Scope

This guide documents expected migration from the latest v1.x release to v2.0.0 before release preparation. It is based on the completed v2.0.0 public API audit, package exports audit, and README finalization work.

This guide does not announce the v2.0.0 release. It also does not add release notes.

## Breaking changes

No breaking public API or package export change is currently expected from the completed audits.

Users already importing the documented API from the package root should not need code changes for the documented public runtime exports or public type exports when moving from the latest v1.x release to v2.0.0.

This is an expected non-breaking migration for the audited public package surface. It is not a guarantee that every application-specific integration needs no review.

## Supported imports

Continue importing runtime APIs from the package root:

```ts
import {
  FlowProvider,
  useFlow,
  useFlowProgress,
  useFlowFrame,
  useWheelInput,
  useTouchInput,
  useKeyboardInput
} from "r3f-interactive-flow";
```

The existing public runtime exports remain:

- `FlowProvider`
- `useFlow`
- `useFlowProgress`
- `useFlowFrame`
- `useWheelInput`
- `useTouchInput`
- `useKeyboardInput`

The existing public type exports remain documented:

```ts
import type {
  FlowFrameCallback,
  FlowFrameState,
  FlowInputTarget,
  FlowTransitionBaseOptions,
  FlowTransitionOptions,
  UseKeyboardInputOptions,
  UseTouchInputOptions,
  UseWheelInputOptions
} from "r3f-interactive-flow";
```

Internal subpath imports are not public package exports and should not be used:

- `r3f-interactive-flow/react`
- `r3f-interactive-flow/r3f`
- `r3f-interactive-flow/input`

## Checklist

Before release preparation, verify your project follows the documented public boundaries:

- Imports use the package root: `r3f-interactive-flow`.
- `FlowProvider` wraps components that call `useFlow`, `useFlowProgress`, `useWheelInput`, `useTouchInput`, or `useKeyboardInput`.
- `useFlowFrame` is called only from React Three Fiber components rendered inside `<Canvas>` and under `FlowProvider`.
- Input hooks run from client-side DOM/input layer components, not from R3F scene objects by default.
- Peer dependencies are installed by the application: `react`, `react-dom`, `three`, and `@react-three/fiber`.
- Next.js App Router usage is placed in Client Components.

## Next.js App Router projects

Use `FlowProvider`, `useFlow`, `useFlowProgress`, `useFlowFrame`, and input hooks from Client Components. Server Components can pass serializable data into a Client Component wrapper, but should not render `FlowProvider` or call flow hooks directly.

`useFlowFrame` still follows React Three Fiber rules and must be used inside a Canvas-bound component. Input hooks attach browser listeners from effects and should run in client-side DOM/input layer components.

Next.js is not a dependency, and Next.js router integration is out of scope.

## Out-of-scope confirmation

This migration guide does not introduce or document new support for:

- public API expansion
- package export expansion
- source behavior changes
- package metadata changes
- dependency changes
- Next.js as a dependency
- router integration
- visual effects, animation timelines, camera presets, shader APIs, particle APIs, templates, CLI/codegen, or third-party animation wrappers
- npm publishing, git tags, GitHub Releases, or milestone closeout work

## Result

Based on the completed audits, migration from the latest v1.x release to v2.0.0 is expected to be non-breaking for users of the documented package root API. Projects using internal subpath imports should move those imports to `r3f-interactive-flow` before relying on the public package boundary.
